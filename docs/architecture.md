# 架构与数据边界

本文记录**为什么这样设计**，尤其是那些一旦写错就很难回头的决策。
产品设计文档（v0.2）里的约束在这里落成了实现，逐条对应。

---

## 1. 数据边界

| 位置 | 内容 | 读写 |
| --- | --- | --- |
| `BOOKS_DIR` (`/books`) | 用户自己的电子书 | **只读** |
| `DATA_DIR` (`/data`) | SQLite、封面缓存、令牌密钥 | 读写 |
| 客户端本地 | 离线书文件缓存、本地进度 | 读写 |

服务端是唯一真相源。客户端只承担「渲染 + 缓存」。

### 只读挂载的强制手段

`src/config/index.ts` 在启动时断言 `DATA_DIR` 不在 `BOOKS_DIR` 内，否则拒绝启动。
这不是文档里的君子协定，是运行时会拦下来的硬约束。

扫描器与所有文件访问都经过 `src/lib/paths.ts` 的 `resolveInside()`——
唯一的路径解析出口，`../` 逃逸会抛 `PATH_TRAVERSAL`。
扫描时也**不跟随符号链接**：指向挂载点外的软链会读到用户没打算共享的文件。

封面缓存写在 `DATA_DIR/covers/`，不写在书旁边。

## 2. 书籍主键

```ts
id = sha256( (dc:identifier ?? '').toLowerCase() + '\0' + sha256(fileBytes) )
```

### 为什么不用文件路径

用户的真实行为是**持续整理书库**：改名、分目录、加前缀。

| 场景 | 路径做主键 | 当前设计 |
| --- | --- | --- |
| 重命名 `三体.epub` → `刘慈欣 - 三体 (修订版).epub` | 进度全丢 | 进度保留 |
| 移动到另一个目录 | 进度全丢 | 进度保留 |
| 同一本书放两份 | 书架出现两条 | 合并成一条 |
| 重新编码的同名文件 | 误认为同一本 | 视为不同副本 |

第二列是自建书库产品最常见的差评来源，所以这条必须在上线前定死。

### 为什么哈希也要参与

只用 `dc:identifier` 不行：很多自制/盗版 EPUB 没有 identifier，或者多本书共用
一个占位 identifier。只用哈希也不行：同一本书不同来源的副本哈希不同，无法合并。

两者结合：identifier 提供稳定的锚点，哈希保证「字节不同就是不同的副本」。
`identifier` 缺失时退化为纯哈希，行为仍然正确（只是无法跨副本合并）。

### 文件表与书表的分离

`book_files` 记录磁盘上的文件（`rel_path`、`size`、`mtime`），`books` 记录书。
多对一：一本书可以有多份副本。

文件被删时 `missing=1`，不立即删记录——用户可能只是临时拔了移动硬盘。
但一旦这本书已经有了别的可用文件，旧的行就是纯噪声，会被清掉，
否则反复整理书库会让文件表无限增长。

只有「没有任何可用文件」且「用户没手动加进书架」的书才会被删除。
宁可显示一本暂时不可用的书，也不能删掉读者精心整理过的书架条目。

## 3. 增量扫描

两阶段变更检测（`Scanner.indexFile`）：

1. **`mtime + size`**：便宜，跳过绝大多数文件
2. **内容哈希**：权威，确认字节真的变了

只有第一阶段判断"可能变了"才读文件算哈希。所以每 60 秒轮询一次也很轻。

`Scanner.scan()` 对并发调用做去重（共享同一个 Promise），
避免定时器和手动触发同时砸磁盘。

## 4. 元数据优先级链

```
1. 手动修改（metadata_overrides 表）
2. EPUB 内嵌（dc:* + calibre meta）
3. provider 补丁（只填空缺）
4. 文件名解析
```

### 关键实现细节

`books` 表存的是第 2/3/4 层的结果。第 1 层单独一张表，**读取时**叠加
（`ShelfService.toDto` → `applyOverrides`）。

这样做的原因：扫描器可以放心地刷新 `books` 表，因为手动修改根本不在那张表里，
不可能被覆盖。

`books.source` 记录的是**基础值的来源**（`embedded` / `filename` / `provider:x`），
不记录 `manual`。手动修改过的字段由 DTO 的 `manualFields` 单独返回。
保持来源干净，撤销单个字段时才能正确回落到原始值。

### 文件名解析的保守策略

中文电子书里 `书名 - 作者` 和 `作者 - 书名` 都极常见，没有标记时**无法区分**。

因此只在有证据时才切分：

- `《书名》` → 这一侧是书名
- `著` / `编` / `译` → 这一侧是作者
- 一侧是中文人名（2-4 字且首字为常见姓氏）→ 另一侧是书名
- 一侧是拉丁文人名 → 另一侧是书名
- **都不满足 → 整串保留为书名，作者留空**

最后一条是刻意的：漏一个作者，读者手动补一下就好；猜错一个作者，
书就被归到错误的人名下，而且他未必会发现。

其余正则也踩过坑，值得记下来：

- 系列正则 `[【\[]...[】\]]` 里 `\[` 在字符类中不转义，会把分隔符 `' - '` 吃掉，
  导致 `金庸 - 射雕英雄传` 变成 `title=金庸, author=射雕英雄传`。改成显式括号对匹配。
- 「（第1卷）」这种卷标，书名是作品本身，不是「第」。要先剥离再切分作者，
  且剥离要按完整括号组做，否则会留下 `射雕英雄传（第1卷` 这样的半截括号。

## 5. 同步与冲突合并

### 为什么是 last-writer-wins

一台设备属于一个读者。多设备之间不存在"编辑冲突"，只存在"某台设备落后了"。
所以 LWW 是正确语义，不需要 CRDT 或向量时钟的复杂度。

### 墓碑

笔记删除写 `deleted=1` 而不是 `DELETE`。

否则：手机离线时删了一条笔记 → 平板（也离线，数据更旧）重连 → 把笔记推回来 →
已删除的笔记复活。墓碑让这个时序变得无害。

### 批次原子性

`SyncService.push` 整个批在**一个事务**里。断网不会留下写了一半的进度。

### 增量拉取

`GET /api/v1/sync?since=<上次的 serverTime>`。客户端记住上次返回的 `serverTime`，
每次只拿增量。移动网络下重连很便宜。

## 6. 认证与安全

- **scrypt** 做口令哈希（内置模块，无原生依赖）。比较用 `timingSafeEqual`。
- 登录时即便用户不存在也跑一次哈希比较，避免用时间差枚举用户名。
- 访问令牌是 HS256 签名的无状态令牌；刷新令牌是不透明随机串存库，可按设备撤销。
- 改口令 / 停用账号会撤销该用户**所有**会话。
- 每个请求都从库里重读用户，不信任令牌里的 role——停用账号立即失效。
- 刷新令牌**轮转**：用过即废，降低泄露窗口。

### 不要重新引入原生依赖

镜像构建的稳定性直接决定部署成功率，而部署门槛是最大的获客阻力。
`better-sqlite3`、`argon2`、`bcrypt` 都需要构建时的 `make`/`gcc`，
在部分 NAS 环境会直接装不上。

`node:sqlite` 和 `node:crypto` 的 `scrypt` 都是内置的，所以当前依赖树里
**没有任何需要编译的包**。

---

## 7. 向后兼容承诺

自部署用户不会及时升级。所以：

- API 只做加法：加字段、加端点。不改已有字段语义、不删端点。
- 数据库 schema 用 `CREATE TABLE IF NOT EXISTS`，升级时新增列/表，不动旧的。
- 错误响应格式全站统一，客户端可以一直用同一套解析逻辑。

## 8. 客户端渲染

产品设计里的关键决策：**不要直接套 Readium Mobile**。Readium 用 Readium CSS
主动接管排版、覆盖出版方样式，这与本产品「忠实还原精排书设计」的核心差异化
直接冲突。实现落在 `web/`，没有框架 —— 渲染热路径是命令式 DOM 操作，
引框架只会把「最小覆盖」的策略搞复杂。产物 38KB（gzip 12KB）。

### 谁渲染什么

| `kind` | H5 | Android |
| --- | --- | --- |
| `reflowable`（epub） | iframe | WebView（同一份代码） |
| `text`（txt） | iframe | WebView |
| `paged`（cbz / 漫画目录 / 单图） | `<img>` 翻页器 | 原生 Pager |
| `document`（pdf） | iframe | 系统查看器 |

分工的依据是内存而不是速度。一页漫画是一个 JPEG：原生 `ImageView` 走硬件解码
并复用 bitmap，WebView 每页一个合成层、在主线程解码 —— 300MB 的画册在
WebView 里是中端机 OOM，在原生里没事。反过来，可重排文本只有 WebView 实现了
CSS 多栏、内嵌字体、竖排、振假名，原生文本栈重做一遍只会更差。

### 为什么外壳用 Shadow DOM、书用 iframe

这两个问题的答案不同，混为一谈是错的。

**Shadow DOM 挡的不是出版方样式。** 出版方的 CSS 是章节资源，必须进到 root
里才能生效，进去之后它照常给书排版 —— 书本来就该给自己排版。它挡的是反方向：
客户端自身的规则不会漏进书里，`all: unset` / `!important` 影响不到脚注和引用。

**书必须是真文档。** 章节里的 `<img src>` 和 `<link rel=stylesheet>` 是浏览器
自己去请求的，没法带 `Authorization` 头。把章节注入宿主文档的结果是每个插图、
每个样式表都 401 —— 书渲染成无样式无图。iframe 是真浏览上下文，子资源请求是
普通导航，URL 里带什么就发什么。

代价是每次请求要带 token（服务端的 `queryTokenAllowed` 是白名单：仅 GET、
仅 `books/*/assets|cover|content`，触发扫描之类一律不接受 URL 里的 token）。
收益是章节由渲染了三十年文档的引擎渲染，而不是我们祈祷等价的片段。

`srcdoc` 而不是 Blob URL：Blob URL 的 origin 是 opaque，frame 的请求会变成
跨源而被拒。`srcdoc` 继承父文档 origin，改写后的绝对 URL 才能用。

### 分页：`column-fill: auto` 需要确定高度

这是实测才发现的，值得记一笔。多栏布局只在容器高度**确定**时才分栏：
不设高度的 `body` 会撑到内容高度，整章排成一列，`scrollWidth` 等于
`clientWidth` —— 翻页手势完全无效，一章只显示一页。

所以文档被钉在 frame 的视口高度（`100vh` 在 iframe 里就是 frame 自己的视口）。
`body` 上**不能**加 `overflow: hidden`：那会把它自己生成的列也裁掉，第一页之后
的内容永远滚不到。

`scroll-snap` 也去掉了：吸附目标是列边缘，不是我们算出来的页边界，
会让 `scrollLeft` 落在两页之间甚至一次跳两页。

### 服务端为此准备的契约

- `GET /books/:id/manifest` — 打开一本书的**全部**信息，一次往返。
  客户端不必先拿书、再拿结构。
- `GET /books/:id/items?group=N` — 分窗的可寻址结构。`kind` 告诉客户端按
  可重排文本还是固定页渲染。
- `GET /books/:id/toc` — 真正的目录，与分窗分离（见下）。
- `GET /books/:id/assets?ref=<opaque>` — 单个资源，流式，支持 Range。

### 分窗与目录为什么是两个接口

一开始它们是一个。`items` 按窗口返回（epub 40 章、漫画一卷），而客户端要目录时
也去读它，结果是目录显示成「第 1 章 – 第 40 章」—— 服务端的传输边界漏进了 UI。

两者要的性质本来就相反：**分窗**是传输边界，一次只给一点，因为客户端要逐段
下载；**目录**必须完整，否则跳转就是残的。合成一个接口，其中一个必然做错。

分窗还有一个约束值得写下来：**章节不能按下标寻址**。分窗返回的是 spine 的前缀，
所以按窗口内下标算出来的章节，在完整 spine 里指向的是另一章。items 一律按
包内路径寻址（`xhtml:OEBPS/ch1.xhtml`）。这是第一版契约的真实缺陷，改对了
之后客户端的「恢复到上次位置」才稳定。

## 格式层：为什么是注册表

早期版本把格式列表硬编码在三处：扫描器的扩展名白名单、`parseBookFile` 的分支、
以及 content-type 映射表。加一种格式要同时改三处，漏掉任何一处都会得到一个
「文件被扫到了但读不出来」的安静 bug。

现在这一切收在 `src/indexer/formats/`：

```
registry.ts   定义 handler 契约，按扩展名路由
index.ts      import 即注册；import 顺序即优先级
epub.ts  pdf.ts  comic-archive.ts  comic-directory.ts  text.ts  image.ts
```

扫描器和 HTTP 层只与 `registry.ts` 对话。新增格式 = 写一个 handler + 一行 import，
扩展名白名单、`/library/formats` 声明、文件遍历过滤都会自动跟上。

### 两种 handler

格式在结构上确实是两类，所以契约也分成两个：

- **文件型**：一个文件一本书（epub、pdf、cbz、txt、单图）
- **目录型**：一个目录一本书（图片目录、漫画卷）。它们没有自己的文件，
  所以扫描器在文件遍历**之前**先发现它们，再把认领目录里的文件排除在索引之外。

目录认领顺序是**从外往里**（浅目录优先）。反过来的话，`进击的巨人/第01卷/`
会各自成为一本书，读者要跨书架记录去找下一卷；而且同一批页面会以
「系列 + 每卷 + 每页」的形式重复出现。外层优先符合人手动归档的习惯：
外层目录是系列，子目录是卷。

### 章节流式读取

EPUB 与漫画此前每次请求都整包解压（EPUB 走 JSZip）。一本 50MB 画册的每次翻章
都会把整个压缩包读进内存，扫全库时更糟。现在两者都走项目自研的 `ZipArchive`：
只读中央目录，按需解压单个条目，`openStream()` 让 stored 直接读、deflate 走
流式 inflate。

`openBuffer()` 给扫描器用（它刚读完文件算哈希，不必再按路径打开一次）。
内存态和文件态共用 `parseCentralDirectory` —— 两个路径对条目偏移的理解一旦
分叉，表现是某一本书的页面从错误位置读起，只在那个用户那里复现。

### 各格式的取舍

**ZIP 自己实现**（`zip-reader.ts`，只用 `node:zlib`）。项目已有的 JSZip 会把整个
压缩包解压进内存，而漫画动辄几百 MB，扫描器又要遍历全库 —— 用 JSZip 会让首次扫描
真实漫画库时内存爆掉。自研版本只解析中央目录、按需解压单个条目。

**GB18030 探测**（`text.ts`）。中文 `.txt` 里 GBK/GB18030 占比极高，按 UTF-8 读会得到
一片替换字符且无法挽回。做法是先严格解码 UTF-8（非法字节序列直接抛错），失败才回退，
所以合法的 UTF-8 永远不会被误判成 GB18030。

**PDF 不上报页数**。旧实现用正则从页树里抠 `/Count`，很容易匹配到无关的 `/Count`
从而报出错误的页数 —— 客户端的分页和进度条会因此错乱。现在诚实地上报 `null`：
客户端打开文档后自己知道真实页数。猜一个数字比没有数字更糟。

**epub 章节重写资源引用**。章节 XHTML 里的 `images/pic.png` 是相对 OPF 目录的；
客户端是从资源端点取到这份文档的，原样交给 WebView 会让图片、字体、样式表全部 404。
服务端在返回前把这些相对引用改写成指向自己的绝对地址，同时跳过绝对 URL、
`data:` URI 和文内锚点 —— 改写脚注链接会把脚注弄坏。

## 解析器版本：修复怎么到达已入库的书

变更检测是内容哈希驱动的，这带来一个不明显的后果：**解析器的修复不会改变任何
字节**，所以扫描恰好会跳过最需要重读的那些文件。坏结果永久留存 —— 这不是
假设，EPUB 页数一度因为内存态 zip 的读取缺陷全是 `null`，而重跑扫描修不回来。

修法是给解析结果带上版本号：`book_files.parse_version` 记录是哪一版解析器写下
的，`PARSE_VERSION` 提升时强制重解析一次。自部署用户不会按时升级，所以版本
必须跟着数据行走，不能只活在进程里。

配套加了可重复执行的增量迁移。SQLite 不支持 `ADD COLUMN IF NOT EXISTS`，
靠 `duplicate column name` 错误判断已执行过；旧库原地升级，不丢数据。

新增的 `lib/log.ts` 是同一件事的另一半：扫描器和解析器跑在定时器里，没有请求
可以借 logger，于是失败是静默的 —— 静默正是上面那个 bug 得以存在的原因。

## 书籍主键的补充规则

`dc:identifier + 内容哈希` 对 EPUB 够用，但对没有内嵌标识的格式（txt、漫画）不安全：
它们唯一能锚定的就是内容哈希，于是在原文件上追加一章会算出新的 id，
**读者的进度就留在旧记录上了**。这在 txt 长篇上尤其明显。

补的规则是：如果同一个路径上次已经解析出一个 id，且新旧两边的「标识锚」
相同（通常都是空），就沿用旧 id。也就是说**原地编辑算更新，不算新书**。
路径只用来查找上一个 id，从不直接参与计算 —— 移动或重命名仍然走内容哈希规则，
所以进度照旧保留。
